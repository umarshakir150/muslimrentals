# designer analysis

**Task:** 20260826-004717-design-and-build-the-first-production-ready

## Summary

Designed the MVP flow for Roommate Profiles (create/edit/deactivate/browse/detail), grounded in the existing Listing/ListingCard/ListingFilters/users.ts public-profile patterns. Kept it to plain filtering (audience, city, budget, move-in timeframe) — no matching algorithm, no filtering by granular personal/lifestyle attributes. Flagging two items for Engineering/Legal before build.

## Findings

1. **[MEDIUM]** Messaging is currently hard-scoped to listings (Conversation.listingId is required, non-nullable), so there is no existing path to contact a roommate-profile owner without also touching the Conversation model.
   - Evidence: rentals/backend/prisma/schema.prisma Conversation.listingId is a required field; rentals/backend/src/routes/messages.ts startConvSchema requires listingId.
   - Recommended action: Add an optional roommateProfileId to Conversation and make listingId optional, mirroring the existing nullable Report.listingId pattern. Additive/non-destructive; Engineering to confirm sizing.
2. **[MEDIUM]** Filtering *people* by an audience/gender-style category (even reusing the existing ListingAudience enum) carries different discrimination-risk semantics than filtering listings, since it profiles a person rather than a housing unit.
   - Evidence: company/product.md / ListingAudience enum (BROTHERS/SISTERS/COUPLES/FAMILIES/ALL) in rentals/backend/prisma/schema.prisma; task's Legal instructions on human-rights/discrimination risk.
   - Recommended action: Legal to issue-spot before this ships; kept the field itself (useful for the platform's actual purpose) but deliberately excluded all other personal/lifestyle attributes from being filterable to limit exposure.
3. **[LOW]** Precise location (lat/lng/address) on a public-facing people-directory is a stalking/safety risk beyond the risk profile of listing addresses (which are units, not individuals).
   - Evidence: company/users.md roommate-seeker safety concerns; existing Listing.lat/lng/address fields.
   - Recommended action: RoommateProfile should only ever store/display city-level location, never precise coordinates or address.

## Open questions

- Should the create-profile form be a modal (like PostListingModal) or a dedicated page, given it has fewer fields than a listing? Recommend modal for consistency, but Frontend/Engineering can decide based on final field count.
- Should keyword search over profile bios be included in browse filters for MVP, or deferred? Recommend deferring unless trivial to add, to keep MVP scope tight.

## Recommendation

Build /roommates (browse), /roommates/[id] (detail), and a create/edit form (modal, mirroring PostListingModal) with this field set and flow. Fields — never publicly exposed: exact address/lat-lng, phone, email, exact birthdate (age range only). Profile fields: bio (free text, 20–500 chars), seekingAudience (reuse the existing ListingAudience enum/values: BROTHERS/SISTERS/COUPLES/FAMILIES/ALL — same badge component/colors as listings, for visual+semantic consistency), city (reuse CityAutocomplete, city-level only, no precise location), budget range (min/max monthly, like Listing.price), move-in timeframe (select: ASAP/Within 1 month/Flexible — not an exact date), age range (optional band select, e.g. 18–24/25–34/35–44/45+), and a capped multi-select of self-descriptive lifestyle tags (max 6, fixed vocabulary, e.g. non-smoker/practicing/pet-friendly/student/works) — informational display only, NOT filterable in browse, to avoid person-level filtering on sensitive attributes. Status: soft ACTIVE/INACTIVE (owner-controlled, "Hide profile" not "Delete") + REMOVED (moderator-only), same soft-status pattern as Listing.status — no hard delete in this MVP. Gate both browse and detail behind authentication (unlike public listing browse) since this is real people's personal data — signed-out visitors get a "Sign in to browse roommate profiles" gate, not a blocked/broken page. RoommateProfileCard mirrors ListingCard structure (badge, budget "price" badge, truncated bio, tags capped at 3 with "+N", Message CTA) for UI consistency. Detail page: Message + Report CTAs for other users' profiles; Edit + Hide-profile CTAs when viewing your own. New UI states Frontend must build: signed-out gate (browse+detail), no-profile-yet empty state with create CTA, zero-results filtered-empty state with reset, loading skeletons for grid+detail, inline form validation errors, success toasts (created/updated/hidden/reactivated), a reassuring reversible-action confirm modal for "Hide profile" (not "Delete" — copy should state it's reversible and data isn't lost), a "profile no longer available" state for removed/hidden profiles hit by direct URL, and a "Report profile" modal reusing the existing listing-report UI pattern rather than building a new one. Two flags before Engineering finalizes scope: (1) Trust & Safety — recommend reusing the existing Report model by adding a nullable roommateProfileId FK (mirrors Report.listingId), reusing the existing report modal/reason taxonomy rather than inventing new moderation UI. (2) Engineering/Backend — Conversation.listingId is currently required, so there's no way today to message a roommate-profile owner; recommend making it optional and adding an optional roommateProfileId (same nullable-FK pattern as Report), which is additive/non-destructive and keeps "Message" as the only contact path (no raw contact info ever shown on a roommate profile). This is a necessary supporting change beyond the new RoommateProfile table — call it out explicitly in the implementation report, not silently. Legal should issue-spot: reusing the audience/gender-style categorization on person profiles (not just listings) and the optional age-range field for discrimination/human-rights risk under Canadian shared-accommodation exemptions, plus PIPEDA-relevant concerns for this new category of personal data (bio, age range, budget) being collected/displayed. No founder approval gate needed at the design layer — no payment features, no irreversible actions, schema changes are additive.
