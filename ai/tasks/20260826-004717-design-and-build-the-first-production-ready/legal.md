# legal analysis

**Task:** 20260826-004717-design-and-build-the-first-production-ready

## Summary

Issue-spotting review of the proposed Roommate Profiles MVP. Two items are consequential enough to need explicit founder + eventual professional counsel review before this feature can go live (not before it can be built on a branch): (1) whether any profile field is filterable/searchable by a protected personal characteristic, and (2) updating the existing Privacy Policy/Terms pages, which do not currently disclose or cover a public people-directory feature. Everything else below is a standard issue-spot with a recommended mitigation Engineering/Design can implement directly.

## Findings

1. **[HIGH]** Human-rights/discrimination risk depends entirely on whether roommate-profile fields are used as searchable/filterable parameters versus purely descriptive self-disclosure. Ontario's (and most provinces') Human Rights Code generally prohibits housing-related ads/systems from screening on protected grounds (sex, religion, family status, marital status, disability, etc.), but many provinces carry a distinct 'shared accommodation' exemption for roommate situations where the existing occupant shares a kitchen/bathroom with the new roommate. Whether that individual-selection exemption extends to a platform-level search/filter feature (as opposed to one person choosing one roommate) is genuinely unresolved and jurisdiction-dependent — this is not something this task's product/legal context resolves on its own.
   - Evidence: prisma schema ListingAudience (BROTHERS/SISTERS/COUPLES/FAMILIES/ALL) already exists as the app's precedent for a self-selecting community-fit filter on listings; company/users.md frames the roommate seeker as needing 'some assurance of community/lifestyle fit.' No RoommateProfile fields exist yet to evaluate directly.
   - Recommended action: Founder decision + eventual professional counsel review required before public launch. In the interim, Design/Engineering should default to the lower-risk pattern: fields are self-descriptive text/tags the profile owner writes about themselves (e.g. a free-text or short-tag 'about me / what I'm looking for' section, optionally including an ListingAudience-style self-selected community tag), not a structured filter UI that lets browsing users query by protected characteristics of other people. If any filter beyond city/price/move-in-date-type logistics is proposed, flag it to the founder explicitly rather than shipping it.
2. **[MEDIUM]** The current Privacy Policy (rentals/frontend/src/app/privacy/page.tsx) enumerates specific data categories collected today (account info, listing info, messages, usage/device data) and does not mention or disclose a public roommate-profile/people-directory feature. Publishing this feature without updating the disclosure is a PIPEDA transparency/consent gap — users browsing or creating a roommate profile should be told, before the fact, what's collected and who can see it.
   - Evidence: privacy/page.tsx §1 'Information We Collect' lists only account, listing, messages, usage, and device data; no roommate-profile category exists in the current policy text.
   - Recommended action: DRAFT — NOT LEGAL ADVICE — FOUNDER/COUNSEL REVIEW REQUIRED. Do not apply this edit; route to founder for approval per CLAUDE.md before any agent touches privacy/page.tsx: Add to §1: 'Roommate profile information (if you create one): a short description of yourself, your housing/roommate preferences, general location (city/neighbourhood level), and any other details you choose to include. Roommate profiles are visible to other signed-in users of the Platform and can be deactivated by you at any time.'
3. **[MEDIUM]** Terms of Service §5 (Prohibited Content) and §9 (Termination) are written around listings and general account conduct; they don't explicitly reference roommate profiles as a distinct UGC category, even though §5's prohibited-content categories (discrimination on protected grounds, hateful/abusive content) would presumably need to apply to roommate-profile text too.
   - Evidence: terms/page.tsx §4-5 reference 'Listings' and general prohibited content, with no roommate-profile-specific language.
   - Recommended action: DRAFT — NOT LEGAL ADVICE — FOUNDER/COUNSEL REVIEW REQUIRED. Recommend, for founder review, generalizing §5's prohibited-content language to cover 'listings, roommate profiles, messages, and any other content you post' rather than listings only, and adding a line to §2 noting the Platform also facilitates roommate-matching between users, not just landlord-tenant listings. Do not publish without founder sign-off.
4. **[MEDIUM]** A public-facing directory of people (not properties) is a materially different liability/harassment surface than the existing listing-report-only system. Shipping roommate profiles with zero user-reporting path would leave harassment, impersonation, or discriminatory profile content unmoderatable by anyone but an admin who happens to notice it.
   - Evidence: company/architecture.md and company/product.md confirm Report is scoped to listings only today (no userId/messageId target); ai/current-state.md documents this as a known gap.
   - Recommended action: Recommend Trust & Safety scope a minimal report hook for roommate profiles reusing the existing Report model/pattern (e.g. an optional target field) rather than shipping without one — this is Trust & Safety's call to make concretely, but Legal's view is it materially reduces platform liability exposure for an MVP that didn't exist before.
5. **[LOW]** Precise/geocoded location (lat/lng, street-level) is appropriate for a Listing (a fixed property that needs to be found on a map) but is a meaningfully higher stalking/safety risk when attached to a person's roommate profile rather than a place.
   - Evidence: Listing model stores lat/lng and address for map display; no equivalent precedent should be assumed appropriate for a person-profile without re-evaluation.
   - Recommended action: Recommend city/neighbourhood-level location only for roommate profiles, no precise geocoding or live location, consistent with PIPEDA data-minimization and with Trust & Safety's mandate to review location exposure specifically.
6. **[LOW]** No user-initiated account/data deletion endpoint exists platform-wide today. Adding a new category of personal data (roommate profile content) without a deletion path compounds an existing, already-documented gap rather than introducing a new one.
   - Evidence: company/architecture.md 'Known weaknesses' and company/product.md both already flag the absence of user-initiated account/data deletion.
   - Recommended action: This task's own requirement to support 'deactivate/remove roommate profile from discovery' satisfies the MVP need (soft-deactivation, matching the Listing soft-status pattern). True underlying account/data deletion remains a separate, pre-existing gap that should not be solved ad hoc inside this feature — flag it as a known open item, not a blocker for this task.
7. **[INFO]** Terms §3 already requires users to be 18+ to hold an account; reusing existing authenticated-account gating for roommate-profile creation (no new profile it can be created without an account) satisfies this without any new age-verification work.
   - Evidence: terms/page.tsx §3 'User Accounts.'
   - Recommended action: No action needed — confirm Engineering gates profile creation behind the existing `authenticate` middleware, no separate check required.

## Open questions

- Should any roommate-profile field be filterable/searchable by other users (e.g. gender, community-fit tag), or should the browse experience only support logistics-style filters (city, move-in date, budget) with all community/lifestyle fields being descriptive-only? This determines the severity of the discrimination-risk finding above and needs a founder decision, ideally informed by counsel on the applicable provincial human rights code's shared-accommodation exemption scope.
- Does the founder want Roommate Profiles to be visible to any signed-in user (current assumption based on task's 'browse other users' roommate profiles') or restricted further (e.g. only after some verification step)? Affects both the Trust & Safety and Privacy Policy disclosure recommendations above.
- Timing: should Privacy Policy/Terms updates ship in the same release as the feature, or can the feature launch to a limited/beta audience first with disclosure updates following before broader rollout? This is a founder call, not one Legal can make unilaterally.

## Recommendation

Proceed with building Roommate Profiles on a branch, but apply these constraints before founder sign-off to ship: (1) Keep every roommate-profile field non-mandatory and self-descriptive rather than a filterable protected-ground search parameter — mirror the existing ListingAudience pattern (self-selecting text/tag a user chooses to show, not a dropdown Legal/Engineering builds to let other users query "find me a [gender/religiosity-level] roommate") unless the founder explicitly wants filtering, in which case route that specific decision to the founder + counsel before shipping, not to this agent. (2) Store/display location at city or neighbourhood granularity only for roommate profiles — do not reuse the Listing pattern of precise lat/lng or street address, and do not add a live/precise geolocation feature. (3) Include a minimal "report this profile" hook reusing the existing Report model (add a nullable target relation or reuse pattern, per Backend/T&S scoping) rather than shipping a public person-directory with zero abuse-reporting path — Legal's view is this is a materially higher liability/harassment surface than listing reports and should not be skipped for MVP scope reasons. (4) Treat any edit to terms/page.tsx or privacy/page.tsx as a separate founder-approval action per CLAUDE.md — do not have any agent silently publish the draft language below. (5) Before public launch (not before building), have the founder route the discrimination-risk question and the profile-field list to a lawyer familiar with the relevant provincial human rights code(s), since shared-accommodation exemptions to human-rights housing rules vary by province and their applicability to a platform-level directory (versus an individual's private roommate selection) is a real open legal question this agent cannot resolve.
