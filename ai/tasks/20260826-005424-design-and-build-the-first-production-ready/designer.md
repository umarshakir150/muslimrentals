# designer analysis

**Task:** 20260826-005424-design-and-build-the-first-production-ready

## Summary

Designed the MVP flow for Roommate Profiles (create/edit/deactivate/browse/view), grounded in the existing Listing/ListingCard/ListingDetail/browse patterns and the existing public-profile field-exposure model in users.ts. Plain browse + filter, no matching algorithm. Profiles describe a person seeking a room/roommate; profiles for people who HAVE a room to offer are out of scope for this MVP because Listings already serve that case (a person renting out a room posts it as a Listing) — flagged as an explicit framing decision below.

## Findings

1. **[MEDIUM]** The gender field (Brother/Sister) and the openTo household-type field are the two fields most likely to raise Canadian human-rights/discrimination review questions, since they determine who can find/be found by whom in a housing-adjacent directory.
   - Evidence: Existing precedent: Listing.audience (BROTHERS/SISTERS/COUPLES/FAMILIES/ALL) already gates who a rental unit is offered to, and is filterable on /browse today — this is the closest in-app precedent for treating shared/roommate housing preferences as a legitimate, already-shipped filter category.
   - Recommended action: Legal should confirm whether the existing Listing.audience precedent is sufficient cover to carry the same pattern into a person-level roommate profile, or whether roommate profiles need different treatment (e.g. not filterable, display-only) given they describe a person rather than a unit.
2. **[LOW]** Optional age-bracket field is the lowest-value, highest-discretionary-risk field in the proposed set.
   - Evidence: No existing precedent in this codebase for collecting or displaying age/birth data on any user-facing profile (public user profile route only exposes id/name/avatarUrl/bio/createdAt).
   - Recommended action: Legal/Product should decide whether to keep it (display-only, non-filterable) or cut it entirely for a leaner, lower-risk MVP; either is defensible.
3. **[INFO]** Framed Roommate Profiles as 'seeking a room/roommate' only, not a two-sided 'I have a room to offer' profile type, since the latter is already served by Listings (a room-for-rent can already be posted as a Listing).
   - Evidence: company/product.md scope: 'find roommates and create roommate profiles' — doesn't specify directionality; Listings already support posting a single room via the bedrooms field and audience targeting.
   - Recommended action: Flagging this framing explicitly per the task's request to note assumptions — if the founder intends roommate profiles to also represent people offering a room (distinct from posting a full Listing), that's a scope change worth a quick founder check before Engineering builds against the narrower framing.
4. **[MEDIUM]** Messaging a roommate-profile owner requires the Conversation model to support a non-Listing anchor.
   - Evidence: Conversation.listingId is currently a required (non-optional) field per prisma/schema.prisma — every conversation today is anchored to a Listing.
   - Recommended action: Backend/Engineering should make Conversation.listingId optional and add an optional roommateProfileId (additive, non-destructive per CLAUDE.md), and Security should review IDOR/authorization implications of a conversation that can be anchored to either entity type.

## Open questions

- Should Legal explicitly bless the gender + openTo fields before Engineering builds against them, or is the existing Listing.audience precedent sufficient to proceed and only flag it in the final report?
- Keep or cut the optional age-bracket field for this MVP?
- Is the 'roommate profile = seeking only, not offering' framing correct, or does the founder want a two-sided model in this MVP after all?

## Recommendation

Build /roommates as a new top-level page mirroring /browse's structure exactly (Navbar → header/count line → horizontal filter bar → responsive card grid → modal detail view), with a new "Roommates" nav link. Reuse ListingCard's visual language for RoommateProfileCard (rounded-3xl white card, top badge, pill tags, bottom action row) but swap the photo for a circular avatar and drop the Map button (no precise location is collected). Gate the whole /roommates surface (browse + detail) behind authentication — unlike listings, this is personal profile data attached to a real person, not a physical asset, so treat it at the same trust tier as messaging (which already requires auth). Model RoommateProfile as a new, additive, per-user-owned Prisma table with a soft ACTIVE/INACTIVE/REMOVED status (mirror ListingStatus), one profile per user (unique userId), and reuse the existing ListingAudience enum for the 'openTo' (household type they're willing to join) field instead of inventing a new one. Messaging must work from a roommate profile without a Listing — flag to Backend/Security that Conversation.listingId will need to become optional with a new optional roommateProfileId, which is additive but touches an existing model, so Security should specifically review IDOR/authorization on that join. Reuse the existing Report model with a new optional roommateProfileId (mirrors listingId) rather than building new moderation infra, and add a subtle 'Report' affordance in the profile detail modal reusing the existing report-listing modal pattern. MVP field list — public (visible to signed-in users only): name + avatarUrl (from User, no new fields), 'member since' (createdAt), gender (new required 2-value enum: Brother/Sister — this is the field most likely to need Legal's explicit confirmation given discrimination-risk precedent from ListingAudience, do not treat my inclusion of it as final), openTo (ListingAudience enum, default ALL — who they're willing to live with), city (required, reuse CityAutocomplete), budget min/max (optional, monthly CAD, reuse listing price pattern), move-in timeframe (enum: ASAP/Within 1 month/Within 3 months/Flexible — deliberately not an exact date, reduces urgency-exploitation and precision-tracking risk), lifestyle tags (small fixed controlled list akin to ListingAmenity, e.g. Non-smoker/Student/Working professional/Prays regularly/Quiet household/Halal kitchen only/Pet-friendly/No pets — NOT freeform, to bound moderation and discriminatory-content risk), bio (free text, cap at 500 chars matching User.bio precedent). Explicitly excluded from the model entirely (not just hidden): email, phone, precise address/lat-lng, exact date of birth, and any real-time/last-active presence signal — none of these are necessary for the stated compatibility purpose and all raise stalking/scraping/enumeration risk per Trust & Safety's brief. Age: optional self-disclosed bracket (e.g. 18-24/25-34/35-44/45+), display-only, NOT a filter option in this MVP — flag to Legal as a field to confirm before treating as final, and to Product as a candidate to cut entirely if Legal is uneasy, since it's the lowest-value field in the set. New UI states Frontend must build (do not miss these): (1) loading skeleton grid on /roommates (reuse browse's pulse pattern), (2) zero-results-after-filter empty state (reuse browse's copy pattern), (3) brand-new-signed-in-user-with-no-profile-yet banner/CTA above the grid ('Create your roommate profile so others can find you'), (4) signed-out auth-gate state on /roommates (new — listings don't need this) with a Sign In CTA rather than a blank page or redirect, (5) create/edit profile form modal (model on PostListingModal's structure/styling) with inline validation errors, (6) deactivate-profile confirmation dialog — reversible, so use neutral (not red/alarming) styling, copy: 'Deactivate your profile? Your profile will be hidden from Browse and can't be found by others. You can reactivate anytime from here.' with Cancel/Deactivate buttons, (7) reactivate affordance shown in place of Deactivate when status is INACTIVE, (8) report-profile modal (near-duplicate of the existing report-listing modal, retargeted), (9) own-profile detail view showing Edit/Deactivate instead of Message/Report (a user can't message or report themselves — Backend/Security should also enforce this server-side, not just hide the button). Do not build a matching/recommendation algorithm or a two-sided 'offering a room' profile type for this MVP — both would duplicate existing Listings functionality and add complexity the task explicitly asks to avoid.
