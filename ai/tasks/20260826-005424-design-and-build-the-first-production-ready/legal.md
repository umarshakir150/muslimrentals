# legal analysis

**Task:** 20260826-005424-design-and-build-the-first-production-ready

## Summary

Reviewed the Roommate Profiles MVP scope for discrimination, privacy/PIPEDA, and platform-liability risk. Biggest issue: applying an audience/gender-preference field to a *person's* profile (versus today's unit-level ListingAudience) raises materially higher human-rights/discrimination exposure that is jurisdiction- and fact-dependent and needs professional counsel before production launch. Secondary issues are consent/disclosure for a new personal-data category, precise-location safety risk, and the need to extend the existing Report model (additively) to cover roommate profiles for UGC/impersonation liability. Nothing here blocks building on a feature branch; the flagged items gate production launch, not development.

## Findings

1. **[HIGH]** Discrimination / human-rights risk: the existing ListingAudience pattern (BROTHERS/SISTERS/COUPLES/FAMILIES/ALL) is described in agents/legal.md as a self-selecting community-fit filter, not a blanket exclusion — that framing matters legally. A Roommate Profile is a *person*, not a unit, so the same audience-style field applied to a person (e.g. 'seeking: brothers only') sits closer to human-rights-protected grounds (sex/gender, family status, marital status, religion) than a listing-level filter does. Provincial human rights codes generally treat 'shared living accommodation' (roommate/room-in-occupied-dwelling situations) differently from renting a whole self-contained unit — some provinces provide a narrower exemption for roommate-selection than for landlord tenant-selection generally. Whether an audience/gender-preference field on a roommate profile is legally defensible depends on (a) whether the arrangement is genuinely shared/occupied-by-owner living space and (b) provincial law, which varies. This is exactly the kind of fact-and-jurisdiction-dependent question that needs professional review, not a confident in-house answer.
   - Recommended action: Product Designer/Engineering may proceed with an MVP field like 'living preference / who I'm looking to live with' worded as a self-description (e.g. 'I'm a sister looking to room with sisters') rather than as an exclusionary filter, consistent with how ListingAudience is already framed. Do not add hard-filterable discriminatory fields (age range, marital status, family status, disability, religion-as-filter) to the browse/search endpoint without founder + counsel sign-off. Flag this specific field's wording and filterability to counsel before wide launch — MVP on a feature branch for founder inspection only is fine to proceed without blocking on counsel, but do not ship to real users until reviewed.
2. **[MEDIUM]** New category of personal data (PIPEDA-relevant): a roommate profile is likely to include self-descriptive personal information (lifestyle, budget, move-in timeline, city/area, possibly religion/gender-related self-description) beyond what Listing already collects. This is a new purpose of data collection/display and should be disclosed to users before they create a profile (consent), and the Privacy page's description of what's collected/shared will become inaccurate once this ships (drift risk noted in agents/legal.md).
   - Recommended action: Do not publish any Privacy/Terms/Safety page copy changes without founder approval per CLAUDE.md — Legal can draft copy (see DRAFT below) but Engineering should not silently ship a feature whose data collection isn't reflected anywhere the user sees before opting in. Recommend an in-product consent/disclosure at profile-creation time (e.g. a short 'this will be visible to signed-in users' notice) rather than only a Privacy Policy update, since that's a lower-friction, more effective consent mechanism and doesn't itself require founder approval to build (it's UI copy in a new feature, not an edit to terms/privacy/safety pages).
3. **[MEDIUM]** No account/data deletion path exists today (confirmed gap per company/architecture.md and agents/legal.md). A roommate profile adds a new place where personal data persists. The existing Listing pattern of soft-status (REMOVED) rather than hard delete is fine for MVP consistency, but note that 'deactivate profile' is not the same as 'delete my data' — if a user asks to have their roommate profile data actually erased, there is currently no path to do that anywhere in the app, not just for this feature.
   - Recommended action: No blocking action required for this MVP (matches existing Listing precedent), but log this as a known gap consistent with the existing note in architecture.md rather than treating it as newly introduced by this feature.
4. **[MEDIUM]** Precise/real-time location exposure risk, compounded for a *person* rather than a unit. Listings already show a location (mitigated somewhat by being a fixed address for a housing unit that will become public regardless — that's the transaction). A roommate profile describing a live person's whereabouts is a materially higher personal-safety and stalking-risk category — this overlaps with Trust & Safety's remit but has a direct legal/liability dimension (platform-facilitated safety incident exposure).
   - Recommended action: Recommend city/neighbourhood-level location only (matching the granularity Product Designer should use, per Trust & Safety's parallel review) — no precise coordinates or exact address on a roommate profile, ever. This is a design constraint Engineering/Designer can resolve without founder approval; flagging here only because it has liability weight.
5. **[LOW]** Platform liability / UGC: roommate profile free-text fields (bio/description) create the same defamation, fraud, and inappropriate-content exposure that listing descriptions already do, plus impersonation risk specific to a profile representing a person rather than a unit. The existing Report model can be extended (additive nullable relation) to cover roommate profiles, consistent with CLAUDE.md's non-destructive schema constraint — this is an implementation detail for Backend/Security, not a legal blocker, but the MVP should not ship without *some* reporting hook given the elevated UGC/impersonation risk of a people-directory versus a listings-directory.
   - Recommended action: Confirm with Trust & Safety that a reporting hook targeting roommate profiles is in scope for this MVP (their remit, cross-referenced here because its absence would be a liability gap, not just a UX gap).
6. **[INFO]** Terms of Service currently make no mention of roommate profiles as a feature/data type; once shipped (even to a feature branch for founder review) the terms/page.tsx content will be out of sync with actual product capability the moment this is enabled for any real user.
   - Recommended action: No action needed while confined to a feature branch. Before any production launch, Terms/Privacy/Safety copy updates are required and must go through founder approval per CLAUDE.md — Legal can prepare draft language on request at that stage.

## Open questions

- Should an audience/gender-preference-style field on a Roommate Profile be filterable/searchable in browse, or self-descriptive/display-only text? This has real human-rights-code exposure that varies by province and by whether the arrangement counts as 'shared living accommodation' under provincial law — recommend professional counsel review before any production launch, not just founder sign-off.
- Does the founder want an in-product consent notice at profile creation (recommended, low-friction) versus waiting to update the Privacy Policy — either is fine for a feature-branch MVP, but production launch needs the Privacy/Terms/Safety pages to reflect the new data category, which requires founder-approved copy per CLAUDE.md.
- Should roommate profiles be visible to any signed-in user, or should there be additional gating (e.g. only after some minimal trust signal) given the elevated harassment/impersonation risk of a people-directory versus a unit-listing directory? This is a Trust & Safety-led call; Legal is only flagging the liability angle.

## Recommendation

Engineering may proceed building the Roommate Profiles MVP on its feature branch now — nothing here blocks feature-branch implementation or founder inspection. Before any production launch (not before this branch is built), two items need resolution above the specialist-agent level: (1) get professional legal counsel review specifically on whether an audience/gender-preference field on a *person's* roommate profile is filterable/searchable versus self-descriptive-only, since provincial human-rights treatment of shared-living-accommodation roommate selection differs from whole-unit landlord tenant-selection and this repo has no existing precedent to follow; and (2) get founder-approved updates to the Privacy/Terms/Safety pages reflecting the new personal-data category before real users can create profiles, per CLAUDE.md's founder-approval requirement for those pages. For the MVP itself: keep location display at city/neighbourhood granularity only (no precise coordinates), keep any audience-style field worded as self-description rather than a hard filter (consistent with existing ListingAudience framing), add a lightweight in-product consent notice at profile-creation time (does not require founder approval, unlike Privacy-page edits), and extend the existing Report model additively (nullable roommateProfileId relation) rather than inventing new moderation infrastructure, coordinating the reporting-hook scope with Trust & Safety.
