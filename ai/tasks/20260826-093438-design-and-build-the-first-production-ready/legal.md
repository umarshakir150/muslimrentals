# legal analysis

**Task:** 20260826-093438-design-and-build-the-first-production-ready

## Summary

Issue-spotting review of Roommate Profiles MVP: main risks are (1) housing-discrimination exposure depending on which fields are collected/filterable, (2) a new category of personal data (bio, photo, preferences, location) with no consent-disclosure or deletion path yet, (3) public exposure of PII in a "real people" directory (higher stalking/harassment risk than a property listing), and (4) Terms/Privacy pages that currently say nothing about Roommate Profiles and must not go live without an update. None of this blocks building on a feature branch, but several items must be resolved before founder-authorized deploy to real users.

## Findings

1. **[HIGH]** Housing/human-rights discrimination risk depends heavily on which roommate profile attributes are collected and, especially, which are used as search filters. A gender/audience-style category (mirroring the existing ListingAudience enum) is a defensible precedent already used elsewhere in this app, and roommate/shared-accommodation arrangements are commonly treated differently under some provincial human rights codes than general tenancy — but this varies by province and is not something to assert as settled. Any field beyond gender/audience category used as a hard filter (age, ethnicity, religious sect/observance level, marital status, disability, family status) meaningfully raises discrimination exposure and should not be added without review.
   - Recommended action: Designer/Engineering should restrict filterable fields to the minimal set needed for the stated purpose (city, budget, move-in date, gender/audience category, amenities-style preferences). Do not add sect/religiosity, ethnicity, age filters, or disability status as filterable/searchable fields. Flag the human-rights-code applicability of the gender/audience filter for professional counsel confirmation before real-user launch — this needs qualified review, not a confident answer here.
2. **[MEDIUM]** Roommate Profiles introduce a new category of personal data (bio, photo, living preferences, possibly city-level location) not currently disclosed anywhere in the Privacy Policy, which today (privacy/page.tsx §1) only lists account info, listing info, messages, and usage/device data.
   - Recommended action: Do not publish Terms/Privacy changes without founder approval per CLAUDE.md. See DRAFT language below for review.
3. **[MEDIUM]** No user-initiated account/data deletion endpoint exists today (company/architecture.md, ai/current-state.md). Roommate Profiles add a new, more sensitive PII surface (bio/photo/preferences about a real person actively seeking to share a home), which increases the practical importance of this existing gap, particularly for PIPEDA's right-to-deletion expectations.
   - Recommended action: MVP should at minimum support user-initiated deactivation (soft status flag, mirrors Listing pattern) removing the profile from browse/discovery. Full data deletion remains an existing company-wide gap, not something this task must solve, but should be flagged again to the founder as increasingly relevant.
4. **[MEDIUM]** A public-facing directory of people (not properties) carries materially higher stalking/harassment/unwanted-contact risk than the existing Listing directory. Public exposure of a phone number, precise location, or full name+photo combination would compound this risk.
   - Recommended action: Recommend contact-gating (via existing messaging system) rather than any public contact info field, and city-level (not precise/geocoded) location only — a stricter posture than the current Listing.contactInfo exposure, which is itself flagged as an architecture weakness worth avoiding rather than repeating.
5. **[MEDIUM]** Free-text bio fields on a public people-directory create user-generated-content risk: discriminatory statements, harassment, defamation, or fraudulent/impersonating profiles, with no current way to report a user or profile directly (only listings are reportable today per Report model scope).
   - Recommended action: Reuse the existing Report model/pattern with a minimal addition to support reporting a Roommate Profile, rather than building a new moderation system — recommend Trust & Safety scope this as in-scope for the MVP given the public-directory-of-people risk profile.
6. **[LOW]** Terms of Service (terms/page.tsx) currently makes no mention of Roommate Profiles, roommate conduct, or platform non-verification of roommate-seekers' identities; §7's liability limitation is scoped to listings/landlords/tenants language only.
   - Recommended action: See DRAFT Terms addition below. Founder approval required before publishing per CLAUDE.md; this task should ship the feature on its own branch without publishing policy copy.
7. **[INFO]** This build stays on a feature branch per task instructions and is not being shipped to real users, so none of the above blocks development. They become launch-blocking only at the founder-authorized production deploy step.
   - Recommended action: Track these as a pre-launch checklist item in the task file, not as blockers to branch-level implementation.

## Open questions

- Does the gender/audience-style filter for roommate matching qualify for a shared-accommodation exemption under the relevant provincial human rights code(s) this platform operates in? Needs qualified counsel confirmation, not an assumption, given the platform serves multiple provinces.
- Should Roommate Profiles require a distinct consent/disclosure step at creation time (separate checkbox/notice) given they involve a new, more sensitive category of self-disclosed personal data than listing creation? No existing precedent in this codebase to follow.
- Who is the intended audience for a Roommate Profile's contact — any signed-in user, or only users who've been granted access via a request/approval step? This affects both discrimination-filter design and harassment/enumeration risk, and no existing pattern in this app resolves it (Listings are public to all; messaging requires a prior conversation).

## Recommendation

Proceed with building the MVP on its own branch. Engineering/Designer should: (a) keep the field set minimal — name/display handle, city (not precise address), gender/audience-style category (reuse the existing ListingAudience pattern as precedent), budget range, move-in timeframe, short free-text bio, optional avatar — and avoid any field capturing religious observance level, sect, ethnicity, or age as a hard filter; (b) never expose phone/email/precise coordinates publicly — gate real contact behind the existing messaging system, mirroring a *stricter* posture than Listing.contactInfo's current public exposure, not copying it; (c) add profile as a reportable target reusing the existing Report model/pattern (minimal schema addition, not a new moderation system) — flag to Trust & Safety as a near-must for a public people-directory; (d) ensure Roommate Profile deactivation is a soft status flag consistent with Listing's soft-removal pattern, not a hard delete, and route it through the same "no user-initiated full data deletion yet" gap already documented company-wide. Before any founder-authorized production deploy: get the two DRAFT policy additions below in front of the founder and, ideally, outside counsel — do not deploy with Terms/Privacy silent on Roommate Profiles.
