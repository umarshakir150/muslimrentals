# trust_safety analysis

**Task:** 20260826-093438-design-and-build-the-first-production-ready

## Summary

Roommate Profiles introduces the platform's first person-to-person "who is this stranger" surface, which is a materially higher trust/safety risk than listings (matching with a person to live with, vs. viewing a unit). The existing Report model/pattern (POST /listings/:id/report, Report.status PENDING→REVIEWED/RESOLVED/DISMISSED, admin review via /admin/reports) is directly reusable and should be extended with a nullable roommateProfileId FK rather than inventing a new moderation system. Key risks: harassment/unwanted contact from a public directory of people seeking housing, enumeration/scraping of personal attributes, discriminatory filtering (audience/lifestyle fields used as search filters), impersonation, and location precision leaking a user's real address/whereabouts. Field-level privacy tiering (public directory vs. authenticated-only vs. never-exposed) is required before this ships.

## Findings

1. **[HIGH]** A public roommate-profile directory materially increases harassment and unwanted-contact risk relative to listings, because it centers on matching with a specific person rather than a place, and because renters currently self-select into contacting a landlord about a fixed unit rather than browsing a directory of individuals.
   - Evidence: company/users.md's Roommate seeker section explicitly flags this: "any roommate-profile feature needs Trust & Safety and Legal review before launch... higher-risk surface for harassment and misrepresentation than listings."
   - Recommended action: Route all profile-to-profile contact through existing in-app messaging (already has typing indicators/read receipts/rate-limited REST fallback) rather than exposing phone/email on the profile itself; do not add a direct-contact field to RoommateProfile.
2. **[HIGH]** No reporting mechanism exists for anything except listings today; shipping a public profile type without an equivalent report path leaves harassment/scam/impersonation profiles with no moderation entry point.
   - Evidence: company/product.md: "Reporting users or messages directly. Only listings are reportable today (POST /listings/:id/report)." ai/current-state.md confirms same gap.
   - Recommended action: Add nullable Report.roommateProfileId (mirrors existing nullable Report.listingId with onDelete: SetNull) and a POST /roommate-profiles/:id/report route mirroring listings.ts:310-319 exactly (reportSchema, authenticate, writeRateLimiter, validateUuidParam).
3. **[MEDIUM]** Precise location data (the lat/lng pattern used for Listing's map features) would be inappropriate to carry over verbatim to a personal roommate profile — it risks exposing a user's real home/whereabouts to any signed-in or anonymous browser, a stalking/safety risk distinct from a rental unit's address being public.
   - Evidence: Listing model (schema.prisma:66-67) stores precise lat/lng and is publicly browsable/mappable; a person is not a fixed rentable unit and should not get the same precision-of-location treatment.
   - Recommended action: Limit RoommateProfile location to city/town granularity only (reuse the existing city/town/province fields' semantics from Listing, but omit lat/lng, address, and neighbourhood-level precision).
4. **[MEDIUM]** Free-text bio fields on a public profile are a vector for inappropriate content, scam solicitation (e.g. asking for e-transfer before meeting), and doxxing of a third party (e.g. naming another user in a harassing context).
   - Evidence: General pattern already acknowledged for listing descriptions in this role's remit ("inappropriate content in listing descriptions, images, messages").
   - Recommended action: Apply the same input validation/length limits Engineering already uses for Listing.description (Zod .strict() schema conventions) to the profile bio field; no new content-moderation tooling is needed for MVP beyond the reporting hook — do not build automated content scanning for this MVP.
5. **[LOW]** A public browse/list endpoint without care in field selection risks enumeration/scraping of personal attributes (e.g. scraping all users' city + budget + audience preference at scale) even if no single field is individually sensitive.
   - Evidence: Principles doc's "explicit safe-field select" convention (company/principles.md) exists precisely to prevent this class of issue on the existing users.ts public-profile route.
   - Recommended action: Backend should apply an explicit Prisma select on the browse/detail endpoints (never a blanket profile object return) and reuse existing rate-limiting conventions on the list route; no new anti-scraping infrastructure needed for MVP.
6. **[MEDIUM]** Filterable/searchable personal attributes beyond the audience categories already used for listings (e.g. hypothetical religiosity level, family status, ethnicity, disability-related fields) would convert a discrimination-risk design decision into a discrimination-risk *searchable* feature, compounding legal exposure beyond what Legal alone should resolve.
   - Evidence: Task instructions explicitly call for Legal issue-spotting on this exact risk given Canada's human-rights/housing-discrimination context.
   - Recommended action: Constrain RoommateProfile filterable fields to the same ListingAudience-style categories already legally load-bearing for the product today; treat any additional filterable personal-attribute field as requiring a founder approval gate before implementation, per this task's own escalation criteria.

## Open questions

- Should the exact PUBLIC-tier field list (bio length limit, whether budget range is shown as an exact number vs. a bucketed range to reduce financial-profiling risk, whether move-in date is exact vs. month-level) be finalized by the Product Designer before Backend implements the Prisma model, or is T&S's proposed tiering sufficient to hand directly to Engineering?
- Does the auto-escalation/priority-review threshold for repeat reports (3+ reports/24h) already exist anywhere in the current admin/report pipeline for listings, or would adding it for roommate profiles only create an inconsistent moderation experience across content types? Recommend confirming with Engineering before building any escalation logic net-new.

## Recommendation

1) Extend Report to support roommate profiles: add nullable `roommateProfileId` FK (mirror `listingId`'s SetNull-on-delete pattern) rather than a new model, and add a `POST /roommate-profiles/:id/report` route that reuses `reportSchema`, `authenticate`, `writeRateLimiter`, and `validateUuidParam` exactly as `/listings/:id/report` does — same admin queue, no new moderation surface. This is a required addition, not optional, since a public people-directory without a report path is a safety gap Backend/Engineering must build in this MVP, not defer.
2) Field exposure tiers for the browse/detail public API: PUBLIC (first name or display name only — never last name, city/town only — never precise lat/lng or street address, audience/roommate-type preference, budget range, move-in window, a short free-text bio, self-selected lifestyle tags drawn from a fixed enum list not free text where discrimination risk exists e.g. no religiosity-level or family-status filters, listing/profile creation date). AUTHENTICATED-ONLY (nothing additional recommended for MVP — do not add a "reveal more once logged in" tier, it adds complexity without a clear MVP need). NEVER EXPOSE IN BROWSE/DETAIL (email, phone, exact address/geo-coordinates, any contact info — mirror how Listing's `contactInfo` is only meant to be exchanged via in-app messaging, not the profile page itself; profile-to-profile contact should go through existing messaging, not a public phone/email field). Route the exact PUBLIC field list to the Product Designer/Backend for final sign-off since it's a design/schema decision, but T&S requires the NEVER-EXPOSE list be enforced via an explicit Prisma `select` (per `company/principles.md`'s "explicit safe-field select" model) on every public/browse read.
3) Rate-limit and de-enumerate the browse/list endpoint the same way listing browse likely already is (pagination, no sequential/guessable ordering advantage) — reuse existing `writeRateLimiter`/read-limiter conventions, do not build new anti-scraping infra for MVP; flag but do not block on this.
4) Auto-flag for priority admin review (vs. normal PENDING queue): reports citing harassment or explicit scam/solicitation-for-money patterns in a roommate profile bio, and any profile reported by 3+ distinct users within 24h (mirrors typical repeat-report escalation — Backend should confirm whether this threshold logic already exists anywhere or needs a small addition; if it doesn't exist for listings today either, do not build it net-new for roommate profiles alone — queue normally like listings currently do, and raise the general "auto-escalation doesn't exist yet" gap to Engineering as an incidental note, not an in-scope build item).
5) Deactivation must be a status flag (e.g. `RoommateProfile.status: ACTIVE|INACTIVE|REMOVED`), not a hard delete, consistent with Listing's soft-removal pattern — this also preserves evidence (message history, profile snapshot, reporter/reported account history) if a report is later filed against a profile the user has since deactivated.
6) Do not filter/search by protected-class-adjacent attributes (gender presentation beyond the existing audience categories already used for listings, ethnicity, religiosity level, family status, disability) — only carry over the same `audience` categories (BROTHERS/SISTERS/COUPLES/FAMILIES) already established and legally load-bearing for listings today, since introducing new filterable personal-attribute fields is a discrimination-risk product decision requiring Legal review and likely a founder approval gate per this task's own escalation criteria, not something T&S or Engineering should resolve unilaterally.
7) No autonomous bans or content removal from T&S — any profile removal beyond an unambiguous policy violation (e.g. profile bio containing explicit contact-info-for-money-upfront scam language, or slurs) goes through the existing admin `/admin/reports` review flow and `PATCH /admin/users/:id/ban` for account-level action, per this role's hard limits.
