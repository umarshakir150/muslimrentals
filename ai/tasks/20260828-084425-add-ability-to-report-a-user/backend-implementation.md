## Summary

Implemented the narrow, additive scope all three prerequisite reviews (designer, trust_safety, legal) converged on: extended the existing Report model (never a parallel table) with a nullable targetType/reportedUserId/messageId/messageSnapshot, and added two new authenticated routes — POST /messages/:id/report and POST /users/:id/report — reusing the exact reason/description Zod .strict() pattern already used by POST /listings/:id/report. Also extended GET /admin/reports to branch on targetType and surface the right review context (reported user's ban state, or the reported message's sender + conversation) so the existing admin triage flow works for the new target types without a separate UI. The migration itself could not be applied/verified against a live Postgres in this sandbox — `prisma migrate dev/status/db push` are explicitly denied by this environment's tool permissions (confirmed directly, matching the prior roommate-profiles attempt's finding) — so I followed the repo's own established fallback for this exact situation (see the two existing hand-authored migrations in prisma/migrations/): hand-wrote the migration.sql to match exactly what `prisma migrate diff` would generate for this schema diff, and validated schema correctness via `prisma validate`/`prisma generate`/`tsc --noEmit` (all clean) instead. This migration still needs to be applied out-of-band via Supabase's SQL execution (per the established pattern) and then reconciled with `prisma migrate resolve --applied` by whoever has real DB access, before these routes can be deployed — flagging this explicitly rather than silently treating it as done.

## Self-check notes

- Endpoints added: POST /messages/:id/report (authenticate + writeRateLimiter + validateUuidParam) — who can create: any authenticated user who is a participant in the message's conversation, verified server-side via conversation.participants lookup (not inferred from request); who can read: only admins via GET /admin/reports (ReportTargetType.MESSAGE branch), never exposed back to the reported sender or other participants; who can modify/delete: none — reports are never editable by their creator, only admin via existing PATCH /admin/reports/:id status/resolution flow (unchanged); self-report blocked (message.senderId === req.user.id -> 400); object IDs are UUID-validated via validateUuidParam and existence + participant-membership is re-checked server-side after DB lookup, never inferred from the request body.
- Endpoints added: POST /users/:id/report (authenticate + writeRateLimiter + validateUuidParam) — who can create: any authenticated user, targeting any other existing user (no prior-interaction requirement was implemented, per trust_safety's open question left unresolved by founder — this is the more permissive of the two options they flagged; can be tightened later if the founder wants prior-interaction-only); who can read: admins only, via GET /admin/reports; self-report blocked before any DB query (req.params.id === req.user.id -> 400); target existence verified server-side (404 if not found) before creating the Report row.
- Data exposure check: POST /messages/:id/report and POST /users/:id/report both return only {success, message} — no report ID, no target's private fields, nothing that could let a reporter enumerate whether a report already exists against that target. GET /admin/reports's new reportedUser/message includes are gated behind the router's existing requireRole(ADMIN, MODERATOR), so no new privilege escalation surface — email exposure to admins there matches the existing pattern already used for reporter.email and GET /admin/users.
- Migration risk: fully additive (new enum type, three new nullable columns, three new indexes, two new FK constraints with SetNull) — no existing column altered, no NOT NULL added to pre-existing data, no destructive change. Explicitly NOT verified against a live database in this session because prisma migrate dev/status/db push are denied by this sandbox's tool permissions (re-confirmed, not assumed) — this is the same structural gap noted in the task brief (mem_480b2bf7) and must be closed by applying the migration out-of-band (Supabase SQL execution, per this repo's own established precedent for its two existing migrations) before these routes go live.
- Deliberately did not implement: reason-taxonomy enum (kept free-text `reason` string matching the existing listing-report pattern exactly, per 'don't invent new patterns' — legal flagged fixed-taxonomy as a future hardening, not a blocker), priority-queue auto-flagging for targets with >=3 pending reports/24h (trust_safety noted this needs no schema change and can be added as a pure query-time enhancement later), and any frontend UI (ReportModal, Inbox affordances) — that is Frontend's scope per the designer's output, not Backend's.
