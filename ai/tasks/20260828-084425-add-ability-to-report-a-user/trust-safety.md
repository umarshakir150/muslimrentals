# trust_safety analysis

**Task:** 20260828-084425-add-ability-to-report-a-user

## Summary

Confirmed the gap directly in code: Report model (rentals/backend/prisma/schema.prisma:204-219) only has a nullable listingId target with no userId/messageId field, and the only report route is POST /listings/:id/report (rentals/backend/src/routes/listings.ts:311-325), gated by authenticate + writeRateLimiter, taking {reason, description}. Message model (schema.prisma:175-188) has no relation to Report at all. This matches company/architecture.md and company/product.md's documented gap: messaging-based harassment currently has no report path, and a malicious message sender (or a user impersonating a landlord in-thread) can only be addressed if the victim reports the whole listing, which is the wrong unit of action and doesn't target the actual abusive content or account.

## Findings

1. **[HIGH]** No report path exists for message-based harassment or user impersonation today — the only reportable target is a listing, so a user being harassed or scammed inside an active message thread has no way to flag the specific message or the sender account; they can only report the listing the thread originated from, which is the wrong target and gives admins no message-level evidence.
   - Evidence: rentals/backend/prisma/schema.prisma:204-219 (Report.listingId is the only target FK); rentals/backend/src/routes/listings.ts:311-325 (only POST /listings/:id/report exists); Message model at schema.prisma:175-188 has no relation to Report.
2. **[MEDIUM]** If a Report can target a Message directly, message content must be evidence-preserved at report time, since messages are ordinary mutable/deletable rows with no soft-delete or audit trail today — a reported message could otherwise be edited or removed before an admin reviews it, destroying the evidence.
   - Evidence: Message model (schema.prisma:175-188) has no isDeleted/edited/audit fields; nothing in the current schema prevents message content from changing between report submission and admin review.
3. **[MEDIUM]** A user-report endpoint needs an explicit self-report block and rate limiting beyond the existing per-route writeRateLimiter, since user-targeted reports are the highest-risk surface for retaliatory/false reporting (e.g. a scammer reporting the victim first to muddy an investigation, or coordinated harassment via mass reporting of one account).
   - Evidence: company/users.md notes 'malicious or retaliatory false reports' as an existing risk for listings; the same dynamic applies with more severity once accounts themselves are reportable, since a false user-report can be used to pressure or intimidate a legitimate landlord/renter.
4. **[INFO]** Recommend NOT introducing a parallel Report model (e.g. UserReport/MessageReport) — a single additive migration on the existing Report table (nullable targetType enum + nullable targetUserId/targetMessageId) keeps this a backward-compatible, low-risk migration and lets the existing /admin/reports triage flow and ReportStatus lifecycle be reused without duplicating admin UI/logic.
   - Evidence: Existing Report model already uses a nullable FK pattern for listingId (schema.prisma:215-216), which is directly extensible to additional nullable target FKs without breaking existing listing-report rows.

## Open questions

- Should reporting a user be restricted to users who have an existing conversation/listing interaction with the target, or open to any authenticated user reporting any account? Restricting to prior interaction reduces mass-reporting/harassment-via-reports risk but may block legitimate reports of e.g. a suspicious profile seen only in a listing context.
- When mem_480b2bf7 (no reachable dev Postgres) is resolved, does Engineering want to batch this migration with any other pending schema changes to reduce total migration count, or ship it standalone given its trust/safety priority?
- Should the priority-queue auto-flag threshold (≥3 pending reports/24h) apply per-target across both listing and the new user/message report types, or be tracked separately per target type to avoid one abusive coordinated-reporting campaign inflating a single account's queue priority artificially?

## Recommendation

Approve building this, but scope the first cut to minimize migration risk per the DB-migration verification gap (mem_480b2bf7): add a single nullable `targetType ReportTarget` enum (LISTING/USER/MESSAGE) plus nullable `targetUserId`/`targetMessageId` FKs to the existing Report model rather than a parallel model — this is one additive, backward-compatible migration (all new columns nullable, existing listing-report rows unaffected) instead of a schema split, which reduces both migration surface and rollback risk. Do not implement until either (a) the dev Postgres reachability gap blocking bl_368a454b is resolved so `prisma migrate dev` can be verified, or (b) Engineering explicitly accepts and documents the risk of authoring this migration unverified. Required scope for Engineering/Backend: new routes POST /messages/:id/report and POST /users/:id/report (authenticate + writeRateLimiter, same reason/description Zod .strict() schema as the listing route), each validating the target exists and that the reporter is not reporting themselves (self-report block on /users/:id/report), and each snapshotting the message body / reported user's public profile fields into the Report row at creation time (or a linked snapshot) since messages can later be deleted and profile fields can change — the admin reviewer needs to see what was actually reported, not a live-mutable reference. Extend the existing admin /admin/reports UI to branch on targetType and show the right context (message body + conversation participants, or reported user's listing/report/ban history) rather than building a separate review surface. Automate: rate-limiting repeat reporters and flagging a target with ≥3 pending reports from distinct reporters within 24h for priority queue (same PENDING status model, just a priority flag/sort, no new enum state needed). Do not automate: any content removal or account action — a message-harassment or user report must stay in the existing manual admin review flow (PENDING → REVIEWED/RESOLVED/DISMISSED) with any resulting ban going through the existing ADMIN-only PATCH /admin/users/:id/ban, per the hard limit that Trust & Safety recommends, never executes, bans.
