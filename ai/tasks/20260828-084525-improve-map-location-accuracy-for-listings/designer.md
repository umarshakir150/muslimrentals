# designer analysis

**Task:** 20260828-084525-improve-map-location-accuracy-for-listings

## Summary

Reviewed the posting flow (PostListingModal + CityAutocomplete pattern) and the map (FullMap.tsx). Good news: clustering + spiderfy for Part B is largely already implemented — leaflet.markercluster is already wired up with `spiderfyOnMaxZoom: true`, `disableClusteringAtZoom: 14`, and a count-badge cluster icon, and the library's touch/click-away collapse behavior is built in. The real design gap is Part A (required neighbourhood) and making the resulting accuracy actually visible to users, not just stored.

## Findings

1. **[INFO]** Marker clustering and spiderfy-on-max-zoom are already implemented in FullMap.tsx via leaflet.markercluster (spiderfyOnMaxZoom: true, disableClusteringAtZoom: 14, maxClusterRadius: 50), so Part B is mostly a verification/config task, not new UX design.
   - Evidence: rentals/frontend/src/components/map/FullMap.tsx lines 74-92
2. **[MEDIUM]** A hard-required Neighbourhood field will produce a posting dead-end for any city with no seeded neighbourhood entries yet, since the poster has nothing to select.
   - Recommended action: Scope the required-on-submit UI/validation to only cities that currently have a non-empty neighbourhood list; treat full seed coverage of every existing City-table city as a prerequisite for a universal hard requirement, and get explicit Backend/founder sign-off on which approach ships first.
3. **[MEDIUM]** Neighbourhood is being captured purely as a geocoding input in the current task scope; without also surfacing it as visible text on map popups/listing cards, the added location accuracy isn't legible to end users, which undercuts the trust goal.
   - Recommended action: Add neighbourhood display to map marker popups and listing cards/detail pages as part of this task's frontend scope.
4. **[LOW]** Default Leaflet marker icon is smaller than the ~44x44px recommended minimum touch target, which matters more once spiderfy is packing several markers close together at high zoom on mobile.
   - Recommended action: Pad marker hit areas (not just visuals) when Frontend touches marker icon code for this task.

## Open questions

- Does every city currently in the `City` reference table have (or will have) at least one seeded neighbourhood before this ships, or does the required-field UX need a per-city fallback?
- Should the spiderfy interaction get a first-use hint/tooltip (e.g. a one-time '+N tap to see all' label on dense clusters) to improve discoverability on mobile, or is the existing count-badge treated as sufficiently self-explanatory?

## Recommendation

1) Build Neighbourhood as a second, dependent autocomplete directly under City in PostListingModal, matching CityAutocomplete's existing visual/interaction pattern exactly (same input chrome, dropdown, keyboard nav, clear button) — don't invent a new control. It must be disabled/greyed with helper copy \"Select a city first\" until City has a value, then auto-fetch/filter that city's neighbourhood list. 2) Hard-required-on-submit is risky if seed coverage is incomplete: if a selected city currently has zero seeded neighbourhoods, do NOT hard-block posting (that's a dead end that will show up as \"the form won't let me post\" support tickets) — either scope the hard requirement to only cities with a non-empty neighbourhood list (recommended, and matches Part A's DB-nullable/API-required-for-new-listings design), or ship with full seed coverage for every city already in the `City` table before enforcing it everywhere. Escalate this coverage decision to Backend/founder explicitly, don't let it be silently decided by whichever city happens to run out of data first. 3) Field copy: label \"Neighbourhood *\", helper text \"Helps renters find listings near them — pick the closest match,\" placeholder \"e.g. Kensington Market, Downtown...\", inline error \"Please select a neighbourhood\" on submit-without-value, styled identically to existing required-field errors in this form. 4) Make the payoff visible, not just internal: surface the neighbourhood name in the map marker popup (e.g. \"Kensington Market, Toronto\") and on listing cards/detail pages — right now the task only stores it for geocoding, but the actual trust signal (\"this listing is really in this part of the city\") only lands if users can see the label, not just a more-accurate pin position. Flag this to Frontend as an explicit added UI surface, not scope creep — without it the feature is invisible. 5) Map/clustering: confirm at implementation time that leaflet.markercluster's built-in unspiderfy-on-click-away and touch handling actually satisfy requirement #6 (collapse on click-elsewhere/zoom-out/filter-change/navigate-away) rather than re-implementing it — check filter-change and route-navigation cases specifically, since those aren't native map interactions the library handles automatically and may need an explicit `cluster.refreshClusters()`/re-init call. 6) Accessibility: the default Leaflet marker icon (~25x41px) is under the ~44x44px minimum touch target; when Frontend builds/adjusts marker icons for this work, pad the tap-hit area (invisible larger hit box, not just a bigger visual icon) so spiderfied individual markers stay tappable on a phone at high zoom where markers are close together. 7) I have not live-verified this on https://muslimrentals.netlify.app/ or on a real device in this session (no MOBILE_VERIFIED/LIVE_SITE_VERIFIED claim) — recommend a follow-up phone-viewport check of the actual spiderfy interaction once shipped to preview, since discoverability of \"tap a cluster to spread it out\" is the one part of this flow that's genuinely non-obvious without a first-use.
