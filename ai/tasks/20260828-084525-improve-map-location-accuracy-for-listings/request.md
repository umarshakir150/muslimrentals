## Objective

Improve map location accuracy for listings and require neighbourhood at posting time, then add marker clustering + spiderfy on the map.

Background: rentals/backend/prisma/schema.prisma's Listing model already has an optional `neighbourhood String?` field (not a new column) and required `lat Float`/`lng Float`. Today PostListingModal.tsx only resolves lat/lng from the selected CITY (via CityAutocomplete, which calls GET /cities/all against the `City` reference table seeded with real Canadian city coordinates) -- there is no neighbourhood-level resolution, so every listing in a city gets the same city-center coordinates regardless of which part of the city it's actually in. The map (FullMap/MiniMap, Leaflet-based per company/architecture.md) currently plots raw lat/lng with no clustering, so many listings sharing a city center overlap into an unreadable pile of markers.

Part A -- required neighbourhood + real coordinates:
1. Make `neighbourhood` a required field in the Post Listing form and in the backend's Zod create-listing schema (rentals/backend/src/routes/listings.ts). Decide carefully whether the DB column itself should become NOT NULL: this table already has real production rows with `neighbourhood` null today, so a hard NOT NULL migration needs either a real backfill (do not fabricate data) or should stay nullable at the DB level while being enforced as required at the API/Zod layer for all NEW listings -- your call, but document the reasoning and do not silently break/crash on existing null rows.
2. Resolve city+neighbourhood to real coordinates, not the city's center point and not guesses. This sandbox's network egress is unreliable/often blocked to arbitrary external APIs (a live per-request geocoding call may not be reachable at runtime), so the most reliable approach -- and consistent with how the existing `City` table was built (prisma/seed.ts, real curated Canadian city data with real lat/lng) -- is likely a similar curated `Neighbourhood` reference table (city + neighbourhood name + real lat/lng), researched via WebSearch/WebFetch for real, well-known neighbourhoods in the cities this product already serves (see the City list), then seeded server-side, with CityAutocomplete-style autocomplete driving selection during posting the same way city selection already works. If you instead find a genuinely reliable, reachable geocoding API (e.g. Nominatim/OpenStreetMap) that works from this environment, that is also acceptable -- verify it actually works before relying on it, do not assume. Either way, do not hardcode a fake/approximate single coordinate per city and call it "neighbourhood-level".
3. Store the resolved coordinates on the listing exactly as lat/lng are stored today. Existing listings and existing map/browse filters (radius search, [lat,lng] index) must keep working unchanged for listings that predate this change.

Part B -- clustering + spiderfy on the map:
4. Implement marker clustering (nearby listings collapse into a single cluster marker showing a count at lower zoom; clusters separate naturally as the user zooms in) using a well-established Leaflet clustering library compatible with react-leaflet if one is already in use, or a solid alternative -- check what's already installed before adding a new dependency.
5. When multiple listings share the same or nearly-identical coordinates and are still overlapping at high zoom, clicking/tapping the shared marker should "spiderfy": individual markers branch outward from the shared point in a small radial/circle pattern (subtle connecting lines are a nice-to-have, not required), each independently clickable and opening the correct listing's preview/details. This is presentation-only -- never mutate/offset the actual stored lat/lng, only the rendered marker position.
6. Spiderfied state must cleanly collapse/reset on: clicking elsewhere on the map, zooming out, changing filters, or navigating away from the map. Must work on both desktop (click) and mobile/touch (tap) -- do not rely on hover for any of this.

Regression coverage (permanent, not one-off manual checks): add automated tests -- this repo now has Vitest set up in both rentals/backend (tests/) and rentals/frontend for exactly this purpose -- covering: neighbourhood required on listing creation (schema rejects a request missing it, per your Part A design), city+neighbourhood coordinate resolution producing real distinct coordinates (not silently falling back to city center), and clustering/spiderfy logic that can be tested without a real browser (e.g. the pure grouping/offset-calculation logic, not full Leaflet DOM rendering if that's impractical to test).
