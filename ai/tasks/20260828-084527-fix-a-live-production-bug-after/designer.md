# designer analysis

**Task:** 20260828-084527-fix-a-live-production-bug-after

## Summary

Sanity-checked whether the reported "map stays visible after navigating away from /map" bug could be a legitimate transition/animation being misread. It is not: there is no route-level transition mechanism in this app (no AnimatePresence/framer-motion page-transition wrapper in layout.tsx or app/map/page.tsx — framer-motion is only used for local component effects like modals/toasts, not route changes), so any map content persisting into Login/Sign Up/Browse/listing pages is unambiguously a leftover-instance bug, not an intentional fade/exit animation. Code reading of FullMap.tsx and MiniMap.tsx surfaces a concrete, plausible root cause matching the repro: both components initialize Leaflet inside an async IIFE (`await import('leaflet')` [+ `leaflet.markercluster` for FullMap]) inside a `useEffect`, but the effect's synchronous cleanup closure only removes the map if the async assignment (`mapRef.current = map` / local `map` var) already completed by the time cleanup runs. If a user navigates away from /map before that dynamic import resolves (very plausible on first visit to /map, on mobile/slower connections, or on a quick click), the effect's cleanup fires while the map hasn't been created yet, does nothing, and then the async callback finishes after unmount and proceeds to call `L.map(...)`, attach the tile layer/marker cluster/click listeners/ResizeObserver, and set global `window.__mapListingClick` — with no cleanup ever registered for that now-orphaned instance, since the effect's return function already ran. FullMap's ResizeObserver-disconnect logic has the same race (it's read off `containerRef.current`, which the same unmount already nulls). This matches the "Leaflet instance never .remove()'d due to a mount/cleanup race" pattern flagged in the task brief, not a CSS/z-index/stray-portal issue and not a legitimate animation.

_No findings._

## Open questions

- Does the same leak reproduce via the browser's native back/forward buttons specifically (bfcache/history restore), or only via in-app Link navigation? These are different mechanisms and QA should test them separately so a fix for one doesn't get credited for fixing both.
- Is /map typically the user's first-ever route visit (cold dynamic-import chunk load, worse race window) or usually visited after other pages (warm cache, narrower race window)? Affects how reliably QA can reproduce it locally vs. why it reads as consistently reproducible in production for the founder.

## Recommendation

Treat this as confirmed, not a false-positive/animation mixup — proceed straight to Frontend implementing a fix, no Designer-side flow/copy change is needed since this is a pure cleanup bug with no new UI states. Concretely ask Frontend to: (1) add an isCancelled/isMounted boolean captured at effect start and checked immediately after each await in the async IIFE in both FullMap.tsx and MiniMap.tsx — if cancelled, call .remove() on the freshly created map instance immediately and bail out before attaching the tile layer/cluster/listeners; (2) make sure the cleanup closure sets that flag first, before doing anything else, so it works regardless of whether the async init has completed yet; (3) capture the container DOM node into a local variable at effect start (not solely containerRef.current) so the ResizeObserver-disconnect logic in FullMap's cleanup doesn't depend on a ref that may already be null; (4) separately smoke-test back/forward browser navigation (not just Link clicks) since that goes through the browser's own bfcache/history restore path, a distinct mechanism from the React-unmount race, and needs its own check — flag to Engineering Lead if that path shows a second, separate leak so it isn't conflated with this fix. No new empty/loading/error/destructive-confirm states are needed for this task — it's invisible cleanup plumbing, not a user-facing flow change. For the regression test: mount FullMap/MiniMap with leaflet/leaflet.markercluster mocked so the dynamic import can be deferred (e.g. an unresolved promise), unmount the component before resolving it, then resolve the import and assert map.remove (or the mocked constructor) was never left dangling — i.e., assert the fix's cancellation flag caused an immediate .remove() call or prevented DOM/listener attachment entirely; document explicitly that this jsdom-level test cannot catch real Leaflet DOM/CSS pane leftovers or actual visual overlap, so a manual/BROWSER_VERIFIED pass (Map → Login, Map → Sign Up, Map → listing, Map → Browse, plus back/forward, on both desktop and a mobile viewport) remains required before calling this done.</parameter>
