# designer analysis

**Task:** 20260901-193457-complete-the-report-a-user-report-a-message-feature-frontend

## Summary

Current codebase has zero report-a-user/report-a-message capability anywhere (schema, backend routes, and frontend UI are all absent, contradicting the prior task's 'backend already built' narrative — only the listing-report window.confirm() exists). Designed a single shared ReportModal (reason picker parameterized by target type, optional description, context preview, proper loading/success/error states) surfaced via a thread-header overflow menu ('Report {name}') and a tap-triggered per-message action in Inbox.tsx, plus a targetType-branching redesign of the admin Reports panel so moderators actually see reported-user/message context instead of 'Listing: undefined'.

## Findings

1. **[HIGH]** The prior task's docs describe backend routes, schema fields, and a migration for user/message reporting as already built and merely 'not wired to frontend' — but none of that exists on the current codebase. `rentals/backend/prisma/schema.prisma`'s `Report` model has only `reason/description/status/reporterId/listingId` (no `targetType`, `reportedUserId`, `messageId`, `messageSnapshot`), `rentals/backend/src/routes/messages.ts` has zero report-related code, and `users.ts` has no `/report` route. `ListingDetail.tsx` still uses `window.confirm()` with a hardcoded reason and no `ReportModal` component exists anywhere in the frontend. This is a full build across schema+backend+frontend+admin, not a 'finish the wiring' task.
   - Evidence: Grep of rentals/backend/prisma/schema.prisma:240-255 (Report model, additive fields absent); grep of rentals/backend/src/routes/messages.ts and users.ts (no report routes); rentals/frontend/src/components/listings/ListingDetail.tsx:79-88 (window.confirm + hardcoded reason); no ReportModal.tsx file exists in rentals/frontend/src.
2. **[MEDIUM]** Admin Reports panel (`app/admin/page.tsx`) renders a flat list assuming every report is listing-shaped (`r.reporter?.name`, `r.listing?.title`, a 'Remove listing' button gated only by `if (!r.listing) return`). Once user/message reports exist, a moderator sees no reported-user identity, no message content, and no sender — just a silent no-op button — which defeats the point of building the report path.
   - Evidence: rentals/frontend/src/app/admin/page.tsx:70-98.

## Open questions

- Should Engineering re-scope this as a fresh full-stack build (schema + routes + migration + frontend + admin) rather than a 'finish the frontend' task, given none of the previously-described backend work is actually present on main?
- Does the founder want a prior-interaction requirement before a user can report another user (flagged low-severity by the prior security review, never resolved) — this is a moderation-policy call, not a UI one.
- Should reporting a message also surface a lightweight 'leave conversation' option, or stay strictly single-purpose this pass? Recommend staying single-purpose.

## Recommendation

Build one shared `ReportModal` (reason picker parameterized by target type + optional description + a short context preview of what's being reported) and use it in three places: (1) replace the `window.confirm()` on `ListingDetail.tsx`'s existing flag button — no schema change needed, ships first as a low-risk validation of the shared component; (2) a 'Report {name}' item in a new thread-header overflow (kebab) menu in `Inbox.tsx`, reporting the other conversation participant; (3) a tap-triggered (not gesture/long-press-only, for accessibility) small action affordance on the *other participant's* message bubbles only — never on the user's own messages — offering 'Report message'. Reason taxonomy must be parameterized per target type: keep 'Misleading or fraudulent listing' only for listings; for users/messages use 'Harassment or abusive behavior', 'Scam or fraud attempt (e.g. asking to pay/send money off-platform)', 'Impersonation' (user only), 'Inappropriate content', 'Spam', 'Other'. Modal states Frontend must build: closed → reason-select → optional description → submitting (spinner, disable submit) → success (toast: 'Report submitted — we review all reports within 24 hours', matching existing listing-report copy) → inline error with retry (not a dead-end toast). All tap targets ≥44px. Do not add a 'block user' affordance in this pass — out of scope, no backend support, and shouldn't be implied by the report UI. On the admin side, make the Reports panel branch on `targetType`: add a small chip ('Listing'/'User'/'Message') per row, and render type-appropriate context — reported user's name/email + a link into the existing admin Users search (don't build a new inline ban button; reuse the existing ban flow to avoid scope creep) for USER reports, and sender name + the `messageSnapshot` text + a link to the conversation for MESSAGE reports — instead of the current code that silently assumes every report is listing-shaped. Before any of this frontend/admin work starts, flag to the Engineering Lead that the schema/migration/routes described as 'already built' in the prior task do not exist on `main` — this needs to be scoped and re-reviewed (Security, Trust & Safety) as new backend work, including actually applying the migration to a real database this time, not resumed as a wiring task.
