# trust_safety analysis

**Task:** 20260901-193457-complete-the-report-a-user-report-a-message-feature-frontend

## Summary

Verified directly against the current repository (commit 49d4bb7, which is also live in production): none of the prior task's backend work is actually present in the codebase today. schema.prisma's Report model has only `listingId` (no targetType/reportedUserId/messageId/messageSnapshot), there is no migration file beyond migration_lock.toml, and neither users.ts nor messages.ts has a report route. This contradicts the task brief's framing that backend routes "were built... but the work never reached production" — in the current codebase there is no backend code to finish wiring the frontend to; it must be (re)implemented from the Aug 28 design, not merely re-exposed. ai/current-state.md (verified 2026-09-01 against the same commit) independently confirms this: "Reporting a user or a message directly — only listings can be reported today." The Aug 28 trust_safety analysis (ai/tasks/20260828-084425-.../trust-safety.md) remains the correct design baseline (additive nullable targetType/reportedUserId/messageId/messageSnapshot fields on the existing Report model, message-content snapshotting at report time since messages are mutable with no audit trail, self-report block, admin panel branching on targetType) and should be re-applied rather than re-derived.

## Findings

1. **[HIGH]** The task brief's premise is inaccurate for the current codebase: no user/message report backend code exists at all today (schema.prisma's Report model, users.ts, and messages.ts show no trace of targetType, reportedUserId, messageId, messageSnapshot, or report routes), contrary to 'backend routes ... were built ... but never reached production.' This must be treated as full-stack new implementation work, not a frontend-only integration task, or the feature will ship with an unreviewed, unverified backend written under time pressure.
   - Evidence: rentals/backend/prisma/schema.prisma:240-255 (Report model has only listingId); no files matched 'report' in rentals/backend/src/routes/messages.ts; migrations directory contains only migration_lock.toml; ai/current-state.md verified against commit 49d4bb7 (live in production): 'Reporting a user or a message directly — only listings can be reported today.'
   - Recommended action: Correct the Engineering Lead's plan to include full Backend re-implementation (schema + migration + routes) with real-DB verification before any Frontend work proceeds, not just UI wiring.
2. **[MEDIUM]** Report-a-message requires evidence preservation at report time: messages are ordinary mutable/deletable rows with no audit trail, so a reported message's content could change or disappear before an admin reviews it unless a frozen `messageSnapshot` is captured in the same transaction as report creation.
   - Evidence: ai/tasks/20260828-084425-add-ability-to-report-a-user/trust-safety.md finding 2; confirmed no isDeleted/edited/audit field exists on the Message model in the current schema.
   - Recommended action: Backend must snapshot message body + sender ID into the Report row atomically with report creation, not rely on a live FK lookup at review time.
3. **[MEDIUM]** Report-a-user has no natural evidence boundary the way listing/message reports do (a listing or message is a fixed artifact; a user account is not) — a false or retaliatory report against a legitimate landlord/renter is the highest-severity misuse case for this feature, especially since there is currently no requirement that the reporter and reported user have any prior interaction (shared conversation/listing).
   - Evidence: ai/tasks/20260828-084425-add-ability-to-report-a-user/trust-safety.md open question 1; company/users.md's documented 'malicious or retaliatory false reports' risk for listings applies with more severity once accounts are directly reportable.
   - Recommended action: Decide with the founder before shipping whether POST /users/:id/report requires a prior shared conversation/listing interaction between reporter and target; until decided, ensure admin review surfaces both accounts' full report/ban history so a moderator can spot retaliatory patterns.
4. **[LOW]** ReportModal's reason taxonomy is a single fixed list including listing-only reasons (e.g. 'Misleading or fraudulent listing'), which is meaningless and confusing when the same modal is reused to report a person or a message.
   - Evidence: ai/tasks/20260828-084425-add-ability-to-report-a-user/qa.json finding 4 (component not present in current codebase, so this must be built correctly from the start rather than patched).
   - Recommended action: Parameterize reasons by targetType from first implementation: LISTING keeps the existing list; USER and MESSAGE get harassment/scam/impersonation/inappropriate-content/spam/other sets appropriate to a person or message target.
5. **[LOW]** Admin dashboard's Reports panel must branch on targetType from the start (it currently has no report-target handling at all, since the underlying fields don't exist yet) — without this, a moderator reviewing a user or message report gets no useful context (reported user's identity/history, message snapshot, sender) to act on.
   - Evidence: ai/tasks/20260828-084425-add-ability-to-report-a-user/security.json finding on admin/page.tsx:70-98 rendering 'Listing: undefined' for non-listing reports in the prior (unmerged) implementation attempt.
   - Recommended action: Build admin UI targetType branching as part of the same implementation pass as the backend fields, not as a follow-up.
6. **[INFO]** Safe-to-automate signals for this feature, consistent with the hard limit that Trust & Safety recommends but never executes bans/content removal: flagging a target with >=3 pending reports from distinct reporters within 24h for priority admin-queue sorting, and the existing writeRateLimiter bounding reporter-side volume.
   - Evidence: ai/tasks/20260828-084425-add-ability-to-report-a-user/trust-safety.md recommendation; agents/trust-safety.md hard limits.
   - Recommended action: Implement as a priority sort/flag within the existing PENDING status, not a new workflow state; keep all bans behind the existing ADMIN-only PATCH /admin/users/:id/ban.

## Open questions

- Should POST /users/:id/report require the reporter to have a prior shared conversation or listing interaction with the target, or remain open to any authenticated user reporting any account? (Unresolved since the Aug 28 review; directly affects false/retaliatory-report risk.)
- Should the >=3-pending-reports-in-24h priority-flag threshold be tracked per target type separately, or combined across listing/user/message reports for the same account, to avoid one coordinated harassment campaign inflating queue priority artificially across unrelated report types?
- Given the backend work must effectively be rebuilt, does Engineering want to re-run Security review on the newly implemented routes/migration before this goes back to Frontend, given the prior Security approval was for code that was never actually merged?

## Recommendation

Before assigning this to Frontend as a "just wire up the UI" task, correct the scope with Engineering Lead: Backend must first (re)implement the schema extension, migration, and both routes against the current schema, verified against a real dev/staging Postgres (not just tsc --noEmit) — this is new implementation work, not integration. Sequence: (1) Backend rebuilds Report.targetType/reportedUserId/messageId/messageSnapshot + POST /users/:id/report and POST /messages/:id/report per the Aug 28 trust_safety design, with self-report block, IDOR check (message report requires conversation participancy), and message-content snapshotted into the Report row at creation time; (2) migration applied and verified against a real database, not deployed to production without founder sign-off per CLAUDE.md; (3) Frontend adds usersApi.report()/messagesApi.report() and wires ReportModal into the user profile view and Inbox (thread-header 'Report user' + per-message report action on the other participant's messages only), parameterizing REPORT_REASONS by target type so listing-only reasons ('Misleading or fraudulent listing') never show for USER/MESSAGE targets — use distinct reason sets: USER → Harassment, Scam/fraud attempt, Impersonating a landlord/agent, Inappropriate behavior, Other; MESSAGE → Harassment, Scam/fraud attempt, Spam, Inappropriate content, Other; (4) admin dashboard Reports panel branches on targetType to show reported user's account/ban history for USER reports and the frozen messageSnapshot + sender identity for MESSAGE reports, instead of 'Listing: undefined'; (5) automate only non-content-affecting signals — flag a target (any type) with ≥3 pending reports from distinct reporters within 24h for priority queue sort, and rely on the existing writeRateLimiter for reporter-side throttling; do not automate any content removal, account restriction, or ban — all resulting bans stay behind the existing ADMIN-only PATCH /admin/users/:id/ban with a founder/admin decision-maker. Resolve the still-open policy question (require prior conversation/listing interaction before a user can report another user, vs. open to any authenticated user) with the founder before this ships, since it directly affects false-report/harassment-via-reporting risk. Route Security and QA to re-review the actual implemented code once built, since no live-DB or end-to-end verification of this feature has ever occurred.
