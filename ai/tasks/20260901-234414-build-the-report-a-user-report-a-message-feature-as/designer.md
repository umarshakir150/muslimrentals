# designer analysis

**Task:** 20260901-234414-build-the-report-a-user-report-a-message-feature-as

## Summary

Confirmed via code review (ListingDetail.tsx:79-88, Inbox.tsx, admin/page.tsx) that no reason-picker UI exists at all today — the current listing "report" is a single hardcoded string behind window.confirm(), not an existing list as the task brief assumed. Designed a shared ReportModal (reason-select → optional description → submit → success/error) parameterized by targetType, plus entry points in ListingDetail, Inbox thread header, and Inbox message bubbles, plus an admin Reports panel branch. LIVE_SITE_VERIFIED: not performed this session (budget-constrained); this design is based on local source review only, not a live/preview inspection.

## Findings

1. **[MEDIUM]** Original task-file description assumed an 'existing reason list' for listing reports that Frontend would extend. That list does not exist in the current codebase — ListingDetail.tsx sends a single hardcoded string ('Inappropriate content') behind a native window.confirm(), with no picker UI at all.
   - Evidence: rentals/frontend/src/components/listings/ListingDetail.tsx:79-88 — handleReport() calls listingsApi.report(listing!.id, 'Inappropriate content') directly after window.confirm(); backend reportSchema (rentals/backend/src/validation/listingSchemas.ts:81-84) accepts any free-text string 5-300 chars, it's not a server-side enum either.
   - Recommended action: Frontend must build the full LISTING reason list as new UI in this pass too, not treat it as pre-existing — scope this into the estimate.
2. **[LOW]** The USER-report prior-interaction requirement is best enforced primarily through UI placement (only ever expose 'Report {name}' from within a shared conversation thread) so the common path never hits the 403, but this is a UX mitigation only — Security/QA must still verify the server-side check independently.
   - Evidence: Task brief mandate: reporter must share a Conversation or have a real listing interaction with the target; task also requires this be enforced server-side regardless of UI.
   - Recommended action: QA test plan should include hitting POST /users/:id/report directly (bypassing UI) for a user with no qualifying interaction and confirm a clear 403, not just rely on the UI never exposing the button in a disqualified state.

## Open questions

- Should the admin Reports panel's per-row type chip use color alone or color+text label for the Listing/User/Message distinction? Recommending text+color for contrast/colorblind accessibility, but confirm with Frontend on existing chip conventions elsewhere in the admin UI.
- For the MESSAGE report entry point, should the tap affordance be a persistent small icon on each bubble or a long-press/tap-to-reveal action sheet? Recommending tap-to-reveal via an already-tappable bubble (consistent with mobile-first, avoids visual clutter on every bubble) but Frontend should confirm feasibility against the existing message bubble component's current tap behavior (e.g. does tapping a bubble already do something, like showing timestamp?).

## Recommendation

Build one shared ReportModal(targetType: LISTING|USER|MESSAGE, targetId, contextPreview) with states closed → reason-select → optional-description → submitting → success-toast | inline-error-with-retry. Reason sets: LISTING = [Misleading or fraudulent listing, Inappropriate content, Spam, Scam or fraud attempt, Other] (this list must be built new — no existing picker exists, contrary to the original task-file assumption); USER = [Harassment or abusive behavior, Scam or fraud attempt, Impersonation, Inappropriate content, Spam, Other]; MESSAGE = same as USER minus Impersonation. Entry points: (1) ListingDetail.tsx flag icon → replace window.confirm with the modal, no schema change; (2) Inbox.tsx thread header → 'Report {name}' action next to the other participant's name, only ever shown for the other participant (never self) so the backend's prior-interaction check is always satisfiable in practice — do not add a generic report-any-user affordance elsewhere this pass; (3) Inbox.tsx message bubbles → a tap-revealed 'Report message' action on the other participant's bubbles only, exposed as a real focusable/screen-reader-reachable button (not gesture-only), never on the user's own bubbles. Keep the current 'we review all reports within 24 hours' neutral copy — never promise removal/ban outcomes, and never reveal to a reporter whether a target already has other reports (matches the {success,message}-only response shape). New states Frontend must build: submitting (disabled controls, no backdrop-dismiss mid-submit), inline error+retry that preserves the user's reason/description, success toast, and a distinct non-alarming dead-end variant ('We couldn't verify a prior interaction to report this user' / close-only, no retry) for the rare 403 case rather than a generic error. Admin Reports panel: add a small text-labelled type chip (Listing/User/Message — not color-only, for contrast/accessibility) per row and branch context rendering: USER rows show the reported user's identity + ban status + a link into the existing admin Users search (reuse the existing ban flow, no new inline ban button); MESSAGE rows show sender identity, the frozen messageSnapshot in a clearly labeled 'message content at time of report' quote block, and a link into the conversation — this replaces the current code path that assumes every report is listing-shaped and shows 'Listing: undefined' otherwise. No 'block user' affordance and no auto-ban/auto-removal UI in this pass, per scope. Trust & Safety and Security should re-check the actual implemented USER-report interaction gate once built (shared-conversation OR listing-interaction), since the UI's assumption that the button only ever appears in a qualifying context is a design mitigation, not a substitute for the server-side check.
