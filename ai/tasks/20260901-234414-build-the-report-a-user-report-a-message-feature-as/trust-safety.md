# trust_safety analysis

**Task:** 20260901-234414-build-the-report-a-user-report-a-message-feature-as

## Summary

Verified nothing has been implemented yet (schema.prisma has no ReportTargetType/reportedUserId/messageId/messageSnapshot fields, no /messages/:id/report or /users/:id/report routes, no ReportModal component) — this is pre-implementation design review feeding Engineering's plan, since there's no code yet for a post-build trust_safety pass. Reviewed the design baseline against abuse cases for message/user reporting, the prior-interaction gate, and admin triage context.

## Findings

1. **[HIGH]** Reported-user identity is not snapshotted at report creation. reportedUserId is a nullable FK with onDelete: SetNull, but the platform's account-deletion flow anonymizes (doesn't hard-delete) User rows. A reported user who self-deletes after a report is filed but before it's reviewed will have their name/email anonymized in the live row, so by the time an admin reviews the PENDING report the reported-user context is useless — this is a self-deletion evasion path for exactly the highest-risk report reason (scam/fraud) the platform cares about most.
   - Recommended action: Route to Backend/Engineering: snapshot the reported user's displayName/email (or a hash) into the Report row at creation time for USER-target reports, the same way messageSnapshot preserves message content against mutation. This is additive (nullable column), consistent with the message-snapshot precedent already specified, and should ship in the same migration.
2. **[MEDIUM]** The 'reporter has saved the target's listing' interaction path is a materially weaker signal than a shared conversation, but the spec treats it as an equally qualifying gate for any report reason including Harassment or Scam/fraud. A user could save a listing (zero contact with the landlord) and then file a high-severity harassment or impersonation report against them.
   - Recommended action: Have GET /admin/reports surface which interaction type qualified the report (shared-conversation vs. saved-listing-only) as part of the review context, so admins can weight credibility — don't silently treat both paths as equivalent evidence in the review UI. Do not block the saved-listing path outright since the founder scope explicitly requires it; just make it visible.
3. **[MEDIUM]** No reporter-side abuse control is specified beyond reusing writeRateLimiter (which throttles request rate, not target concentration). A user could file many reports against the same single target in succession to game auto-flagging/priority-queue heuristics or to harass a legitimate landlord/poster via repeated report noise.
   - Recommended action: Recommend Backend add a simple per-reporter-per-target duplicate/frequency check (e.g. reject or silently no-op a second report from the same reporter against the same target/message within a short window) in addition to the existing global writeRateLimiter. Should be enforced server-side, not just in the UI.
4. **[MEDIUM]** Corroborating-reports-as-priority-signal is listed in my role's remit as something safely automatable, but the current design doesn't specify it, and it needs care: multiple reports against the same target could itself be a coordinated-harassment attack rather than a genuine pattern (e.g. several accounts controlled by one bad actor reporting a legitimate landlord to force review/removal).
   - Recommended action: If Engineering implements priority auto-flagging (noted as future enhancement, not required this pass per spec), it must weight by distinct-reporter *and* reporter account age/history, not raw report count, and must never auto-remove content or auto-ban — only reorder the human review queue. Confirm this stays out of scope for this pass as the spec states.
5. **[LOW]** Self-report blocking on the message endpoint needs to compare against message.senderId specifically, not general conversation participancy — both participants are 'in' the conversation, so a naive check could either wrongly allow self-report or wrongly block reporting the other party's message.
   - Recommended action: Flag to Backend as an implementation-detail test case: reporter must be a participant AND reporter.id !== message.senderId.
6. **[INFO]** GET /admin/reports extension must reuse the existing safe-field `select` pattern (per company/principles.md privacy-by-default) when surfacing reported-user identity and sender identity to admins — no blanket object returns of User/Message rows.
   - Recommended action: Backend should select only fields admins already see elsewhere (name, email, role, ban status, listing ownership) — not expose additional PII (e.g. contactInfo) beyond what's already visible in existing admin user search.

## Open questions

- Should a pending PENDING report against a user block or delay that user's self-initiated account deletion, to prevent using deletion/anonymization as an evasion move? This touches the already-decided account-deletion design and should be a founder call, not inferred.
- Should low-signal interaction (saved-listing-only, no conversation) be restricted to a subset of lower-severity report reasons (e.g. Spam/Other) rather than qualifying for Harassment/Scam/Impersonation reports, or is surfacing it as context to admins sufficient?

## Recommendation

Design is sound and closes the platform's most material T&S gap (only-listings-reportable); proceed with Engineering/Backend/Frontend implementation per the founder-approved baseline, but incorporate the findings above into the plan before build — specifically: (1) snapshot reported-user identity at report-creation time (high priority, mirrors the already-approved messageSnapshot pattern and closes a real self-deletion evasion path), (2) surface which interaction type (conversation vs. saved-listing) qualified a USER report in the admin review context, and (3) add a per-reporter/per-target duplicate-report guard alongside the existing writeRateLimiter reuse. Do not implement automated ban or content-removal in this pass (confirmed out of scope, correctly excluded from the design). Since no code exists yet in this repo, this review is of the design only — a second trust_safety pass against the actual merged implementation (routes, migration, ReportModal, admin panel diff) is required before this is considered ready, per the founder's stated gate requiring QA, Security, and Trust & Safety sign-off on the real code, not the design. No merge/push/deploy should happen until that second pass and Security/QA both clear it.
