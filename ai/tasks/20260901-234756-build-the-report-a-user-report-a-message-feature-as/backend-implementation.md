## Summary

Implemented the backend half of report-a-user / report-a-message from scratch: additive schema extension to Report (targetType/reportedUserId/messageId/messageSnapshot), a hand-authored migration (no live DB in this worktree — see notes), two new endpoints (POST /messages/:id/report, POST /users/:id/report with the founder-mandated prior-interaction gate), and targetType-branched GET /admin/reports. 17 new tests added, all 211 backend tests pass, tsc build is clean.

ENDPOINTS ADDED:
1. POST /messages/:id/report — authenticate + writeRateLimiter + validateUuidParam('id'). Zod .strict() schema (`messageReportSchema`, src/validation/reportSchemas.ts) with a server-enforced enum reason taxonomy (Harassment/abusive behavior, Scam or fraud attempt, Inappropriate content, Spam, Other) plus optional description (max 1000). Looks up the message with its conversation's participants, 404s if missing, 403s a non-participant, 400s a self-report (sender reporting their own message). Snapshots `body` into `messageSnapshot` and `senderId` into `reportedUserId` atomically inside the same `report.create` call (not a later live lookup), since messages are mutable with no audit trail. Returns only {success, message}.

2. POST /users/:id/report — authenticate + writeRateLimiter + validateUuidParam('id'). Zod .strict() schema (`userReportSchema`) with its own enum taxonomy (adds "Impersonation", user-only). 400s a self-report. 404s a nonexistent target. MANDATORY prior-interaction gate enforced server-side via two DB queries run in parallel: (a) `conversation.findFirst` for a shared Conversation where both reporter and target are participants, OR (b) `listing.findFirst` for a listing owned by the target where the reporter either has a conversation about it or has saved it. If neither exists, 403 with a clear message (not a generic error). This is deliberately NOT an open report-any-user endpoint. Returns only {success, message} — no report id, no enumeration of existing reports against the target.

3. GET /admin/reports (existing route, extended) — still gated by the router-level `authenticate + requireRole(ADMIN, MODERATOR)`. Now includes `reportedUser` (id/name/email/isBanned/banReason/createdAt) and `message` (id/conversationId/sender identity) alongside the pre-existing `listing`/`reporter` includes, so LISTING/USER/MESSAGE reports each carry the right review context instead of `listing: undefined` for non-listing reports. Also computes and attaches `reporterHistory` (`totalFiled`/`dismissed` counts via `report.groupBy`) on USER-type reports only, per Trust & Safety's recommendation to help moderators spot retaliatory/bad-faith reporting patterns. No new privilege surface — same role gate as before.

SCHEMA (additive/backward-compatible, prisma/schema.prisma):
- New `ReportTargetType` enum (LISTING, USER, MESSAGE).
- `Report.targetType` — nullable, `@default(LISTING)`, so every pre-existing row (all listing reports) keeps its correct meaning with zero backfill.
- `Report.reportedUserId` — nullable FK to User, `onDelete: SetNull` (mirrors `listingId`'s existing pattern; a reported user's account deletion doesn't erase the report).
- `Report.messageId` — nullable FK to Message, `onDelete: SetNull`.
- `Report.messageSnapshot` — nullable String, frozen message body at report time.
- Added `@@index([targetType])` and `@@index([reportedUserId])`.
- Added the inverse `Message.reports Report[]` and split `User.reports` into `reports` (filed, relation "ReportsFiled") and `reportsAgainst` (relation "ReportsAgainstUser") to disambiguate the two FK relations to User.

MIGRATION: prisma/migrations/20260901235000_add_user_message_reports/migration.sql — HAND-AUTHORED, not generated by `prisma migrate dev`/`migrate diff` against a live database, because no .env/DATABASE_URL exists in this worktree (confirmed: no .env file present). Written to match exactly what `prisma migrate diff` would produce for this schema change (CREATE TYPE, additive nullable ALTER TABLE columns, two indexes, two FKs with ON DELETE SET NULL), following this repo's stated fallback precedent. `npx prisma generate` (via `postinstall`) succeeded against this schema+migration pair, confirming internal consistency, but the SQL itself has NOT been applied to or verified against a real Postgres instance — this must be confirmed (e.g. via `prisma migrate diff` or a real `migrate dev` run) against a live database before this branch is deployed. Called out explicitly per the task's instructions.

OBJECT-LEVEL AUTHORIZATION CHECKLIST (new Report usages):
- Who can create it? Message reports: any authenticated conversation participant except the message's own sender. User reports: any authenticated user except the target, and only with a qualifying prior interaction (enforced server-side, not client-side).
- Who can read it? Nobody via the new endpoints (write-only, {success,message} response). Only ADMIN/MODERATOR can read via GET /admin/reports.
- Who can modify/resolve it? Unchanged — existing PATCH /admin/reports/:id, ADMIN/MODERATOR only.
- Delete: N/A — reports are never deleted, only status-transitioned (existing pattern, untouched).
- Can IDs be manipulated? All three new/extended routes UUID-validate `:id` via `validateUuidParam` and re-verify ownership/participation/interaction server-side from the DB after lookup — never inferred from the request body.
- Could unauthorized data be exposed? No — response shape for both new POST endpoints is `{success, message}` only (matches existing listing-report shape, prevents report-existence enumeration against a target). Admin report list only exposes reporter/reportedUser/sender name+email (already an ADMIN/MODERATOR-only surface, consistent with existing `/admin/users`) — never a non-admin-facing leak.

SCOPE NOTES / DEVIATIONS FROM DESIGN DOC (both intentional, backend-only worktree):
- Did NOT change the existing `POST /listings/:id/report`'s free-text `reason` field to an enum — that endpoint's behavior is unchanged/backward-compatible; only the two brand-new endpoints got server-enforced enum taxonomies (Trust & Safety's core ask was about the *new* gap, not retrofitting the pre-existing listing endpoint, which the task's own design doc says frontend-only "keeps the existing list").
- Did NOT persist which prior-interaction path (shared-conversation vs. listing-interaction) qualified a USER report as a new DB column — the task's schema section enumerates exactly targetType/reportedUserId/messageId/messageSnapshot as the additive fields, and adding another column wasn't in that list. This is a known T&S nice-to-have left for a follow-up if needed.
- This worktree is scoped to backend per its directory/branch name and the assigned "backend" role — frontend (ReportModal, Inbox.tsx, ListingDetail.tsx, admin dashboard UI) is out of scope here and expected to land from the frontend worktree/agent for this same task.
- Legal's data-retention question on `messageSnapshot` (raised by Trust & Safety) was not addressed here — it's explicitly a Legal/founder question per the review, not a backend implementation decision, and no retention/purge job was built (none was requested in the schema/backend scope).
