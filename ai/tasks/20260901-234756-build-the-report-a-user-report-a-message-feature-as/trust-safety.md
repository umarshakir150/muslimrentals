# trust_safety analysis

**Task:** 20260901-234756-build-the-report-a-user-report-a-message-feature-as

## Summary

Reviewed the (not-yet-built) design for report-a-user / report-a-message before Engineering starts. Verified against current code: schema.prisma's Report model has only reason/description/status/reporterId/listingId (no targetType/reportedUserId/messageId/messageSnapshot exist), no /messages/:id/report or /users/:id/report routes exist, no ReportModal component exists, and the existing 'reason' field is unconstrained free text (z.string().min(5).max(300)) rather than an enum — so the 'existing reason taxonomy' referenced in the task brief is a frontend-only convention today, not a server-enforced list. The design (prior-interaction gate for user reports, atomic message snapshotting, targetType-branched admin view, no new privilege surface) is sound and correctly scoped against this platform's top named risk (scams). This is a design-stage review; a second trust_safety pass on the actual implemented code is required before merge, per the founder's stated requirement.

## Findings

1. **[HIGH]** Scam/fraud is this platform's single biggest named risk (company/users.md, company/architecture.md 'Known weaknesses'). The new USER and MESSAGE report paths must treat 'Scam or fraud attempt' as their highest-priority category for eventual triage, even though auto-flagging is correctly out of scope for this pass.
   - Recommended action: Ensure the reason taxonomy's 'Scam or fraud attempt' string is identical/stable across LISTING, USER, and MESSAGE so a future priority-queue enhancement (already deferred per scope item 5) can filter on it without a data migration.
2. **[MEDIUM]** The existing `reportSchema.reason` field is `z.string().min(5).max(300)` — free text, not an enum. The task brief's framing that USER/MESSAGE 'get their own sets' of reasons and LISTING 'keeps the existing list' implies server-side enforcement, but today the taxonomy is enforced nowhere in the backend; the current frontend doesn't even use a picker (ListingDetail.tsx hardcodes the string 'Inappropriate content' via window.confirm()).
   - Recommended action: Have Backend validate `reason` against the applicable per-targetType allowlist server-side (e.g. via a Zod enum keyed off targetType), not just constrain it in the frontend ReportModal, so API callers can't submit off-taxonomy values and admin triage/category reporting stays meaningful.
3. **[MEDIUM]** The prior-interaction constraint on POST /users/:id/report reduces but does not eliminate bad-faith reporting: a user can deliberately initiate a real conversation with a target solely to unlock eligibility to file a retaliatory or harassing false report. This is an accepted tradeoff (still far higher cost than open reporting) but should be visible to moderators.
   - Recommended action: Surface the reporter's own report history (count filed, count dismissed/resolved-against-them) in the admin evidence view for USER reports, and record which qualifying interaction (shared conversation vs. listing interaction) triggered eligibility, so a moderator can spot a report filed immediately after first contact with no other signal.
4. **[LOW]** messageSnapshot introduces indefinite storage of message body text (potentially containing personal information exchanged between two users) inside the Report table, readable by any ADMIN/MODERATOR, with no stated retention or deletion policy — this is a new category of stored user content beyond what currently exists for listing reports.
   - Recommended action: Route a short retention-policy question to Legal per CLAUDE.md workflow step 12 (privacy/data-retention issue-spotting) before merge — does not need to block the build, but should not be silently skipped.
5. **[INFO]** The design correctly avoids introducing any new automated enforcement: both new endpoints return only {success, message} (no enumeration of existing reports against a target), self-report is blocked deterministically, the prior-interaction check is a deterministic DB gate (safe to automate — no judgment call), and all actual restriction/removal decisions remain behind the existing ADMIN-only ban flow and human review. This matches Trust & Safety's hard limits (no autonomous bans, no unilateral content removal).
   - Recommended action: No action needed — confirm this remains true in the implemented code during the required post-implementation review.
6. **[INFO]** Report-priority auto-flagging (e.g., multiple independent reporters against the same target, or a target with an existing PENDING report of the same category) is explicitly deferred per scope item 5. This is a reasonable MVP cut but is a known near-term gap given scams are the top risk.
   - Recommended action: Log as a backlog item for a follow-up task once report volume exists to justify it — not required for this pass.

## Open questions

- Should the server-side reason validation be a hard enum per targetType, or should Engineering keep it free-text server-side and rely on the frontend ReportModal to constrain it (faster to ship, weaker enforcement)?
- What retention/deletion policy should apply to messageSnapshot once a report is RESOLVED/DISMISSED — indefinite, or purged after some period? (Legal question, not Trust & Safety's to decide.)
- Does the admin panel's MESSAGE-report view need surrounding conversation context (a few messages before/after) for moderators to judge intent, or is the single frozen messageSnapshot plus a link to the live conversation sufficient for this pass?

## Recommendation

Proceed with the build as specified, with three additions Engineering should fold into the plan: (1) validate `reason` server-side against the targetType-appropriate allowed list (not just client-side in ReportModal) so the new three-way taxonomy is actually enforced and remains meaningful for admin triage — this is a real gap since the current `reportSchema.reason` is unconstrained free text; (2) in GET /admin/reports for USER-type reports, also surface the *reporter's* own report count and dismissal rate (not just the reported user's history) so moderators can catch retaliatory/false reporting, which is explicitly in Trust & Safety's remit; (3) log/return which prior-interaction path (shared conversation vs. listing interaction) qualified the reporter, stored as evidence context for admin review, not just a boolean gate. Route the new `messageSnapshot` field's data-retention question (indefinite storage of message body text with no expiry/deletion policy, visible to any ADMIN/MODERATOR) to Legal for a one-line retention-policy note per CLAUDE.md workflow step 12 — this is a privacy-adjacent gap, not a blocker. Do not let this ship without a second Trust & Safety review against the actual diff (schema, both new routes, and the admin panel branching) once implemented, since this review is of the design only. No autonomous bans or content removal are introduced by this design — confirmed compliant with hard limits.
